# Engineering skills (Matt Pocock's set)

How the engineering skills (`grill-with-docs`, `tdd`, `code-review`, `implement`, …) bind to this repo.
The flow itself (which skill when, phase boundaries, context hygiene) is owned by `/ask-matt`: when
unsure which skill fits, tell Artem to run it instead of guessing. This file holds only what the
skills cannot learn from looking: how to drive them, where they write here, and which gates they must pass.

## Who can start what

Most flow skills are **user-invoked** (`disable-model-invocation: true`): the agent cannot call them,
so name the slash command and let Artem run it.

- **User-invoked:** `/ask-matt`, `/grill-with-docs`, `/grill-me`, `/wayfinder`, `/to-spec`, `/to-tickets`,
  `/implement`, `/implement-spec`, `/improve-codebase-architecture`, `/triage`, `/handoff`, `/retro`,
  `/setup-matt-pocock-skills`.
- **Model-invoked** (call with the Skill tool when the trigger fits): `tdd`, `diagnosing-bugs`,
  `codebase-design`, `domain-modeling`, `code-review`, `pr`, `prototype`, `grilling`, `research`.

A user-invoked skill is missing from the skill list the harness shows the agent. That does not mean it
is not installed: never reroute to another skill on that basis, ask Artem to type the slash command
([ask-matt docs]).

## Pick the depth before planning

Match ceremony to the change (the alignment ladder):

1. **Tiny, obvious diff** (one file, no new term, no decision): implement directly, then the gate.
2. **Anything larger:** start with `/grill-with-docs`. A grill can graduate into `/wayfinder` if it
   turns out bigger than one session; never start at `/wayfinder` for a well-scoped feature.

## Driving a run

Practice, not skill rules. The base is Pocock's own end-to-end run on a real feature
([video, 2026-11-18](https://www.youtube.com/watch?v=jVBlkOF8sHk)). A rule from his docs, posts or
courses names its source; see [Sources](#sources).

**Grill**

- Open with the problem and why it hurts, not a solution. Leave the design open when it is open.
- Artem sets the pace. At the crux he may say "one question at a time"; once it is settled, "widen out".
  Artem ends the grill. When his answers turn into plain agreement, the agent is aligned: name
  `/to-spec`.
- Propose a new `GLOSSARY.md` term or ADR and wait for a yes. Do not write either mid-grill unasked.
  This overrides `domain-modeling`, which tells the agent to update the glossary inline.
- To choose a name, scenario-test two or three candidates in a table against real sentences from this
  domain. Add one row: "is this how Artem says it?". Drop a candidate that already means something
  else in `GLOSSARY.md` or in a library this repo uses.
- Read the ADRs that touch the area before proposing to change a decision they record.
- Debt found while grilling becomes a GitHub issue, not scope for the current change.
- After `/to-spec`, re-read the spec against Artem's answers. Later steps soften exact ones: numeric
  defaults (caps, timeouts), ordering guarantees, negative requirements ("a timeout never retries").
  Point Artem at its seams and out-of-scope section ([grill-with-docs docs], [to-spec docs]).

**Prototype**

- For a question of feel (tool output shape, interaction, layout), use `prototype` in a background
  subagent with two or three variants while the grill continues. A rejected variant is signal too.
- A prototype is a reference for the spec, not code to merge. Implementers re-implement it under the
  gates; Pocock's retro caught prototype code copied straight into the PR (upstream [#1445], open).

**Spec and tickets**

- At the `/to-tickets` quiz, ask of each ticket "what can be demoed when it is done?"; no answer means
  a horizontal slice. For each acceptance criterion, name the observation that shows it false at the
  base commit: [CODING_STANDARDS.md](../../CODING_STANDARDS.md) § Red first, per ticket ([to-tickets docs]).
- Push back on the ticket count. Each ticket is a fresh window of up to about 150k tokens, so ten
  tickets is a 1.5M-token budget. Merge tickets too small to earn a fresh context (CC-062, RE-074).
- Two tickets that can run in parallel must not touch the same shared file. Here those are
  `docs/tool-catalog.json` (regenerated by `pnpm catalog`), `src/tools/registry.ts`,
  `src/domain/error-codes.ts`, `docs/TOOLS.md` and `GLOSSARY.md`. Add a blocking edge between the
  tickets, or pin the exact names each one adds ([implement-spec docs]).
- A ticket whose check needs a real Calibre library, a real client, a reindex or a release is not
  work for an unattended agent. Label it `ready-for-human` and tell the run to skip it. End the set
  with one manual-QA ticket for Artem that lists those checks (RE-072;
  [overnight-profile.md](../claude/overnight-profile.md) § Prod and live operations).

**Implement**

- Spec and tickets should leave implementers no open decision. An open question goes back to Artem,
  not to the implementer.
- After `/to-tickets`, ask Artem to free the window before `/implement-spec`: `/compact` in his
  2026-11-18 run, `/clear` in the [implement-spec docs]. Either is safe only because the conversation
  is now a published spec and tickets.
- Give a focused sub-problem a fresh subagent instead of reusing one deep in its context.
- The smart zone ends at about 150k tokens on current models (`/ask-matt`; 120k in Pocock's 2026-05
  material, "125K-150K, debated" in his [dictionary][smart-zone], 2026-11). It is a slope, not a
  cliff: past it, finish only what is easy and leave at the next phase boundary (RE-089).
- `/implement-spec` is the run Artem can watch and steer. For truly unattended work Pocock ranks a
  deterministic loop (a script per ticket) above it ([v1.3 post], 2026-10-05). This repo has no such
  script: unattended waves use `overnight-orchestrator`. Both modes obey
  [overnight-profile.md](../claude/overnight-profile.md): merge blockers park for Artem, and nothing
  under "Prod and live operations" runs without him.
- Implementer worktrees hold only tracked files. `docs/dev/` (ADRs, `DECISIONS.md`) and `.claude/` are
  gitignored, so give implementers the absolute path of the main checkout's `docs/dev/adr/` as a
  context pointer. The `*.live.test.ts` suites skip without `RUN_CALIBRE_TESTS=1` and a running
  Content Server, so a green worktree proves nothing about a real library ([implement-spec docs]).
- GitHub's blocked-by count drops only when a blocker closes, and tickets close when the PR merges.
  Tell the orchestrator to compute the frontier from what has merged into the integration branch
  ([implement-spec docs]).

**Review and merge**

- Commit before `code-review`: it diffs `<fixed-point>...HEAD` and cannot see the working tree. Run it
  once, when every ticket has landed. Check the citation on each finding, act on the ones that cite a
  rule or a spec line, then stop. It never comes back clean, and looping it is the spiral that
  [overnight-profile.md](../claude/overnight-profile.md) § Churn guard records ([code-review docs]).
- The one-way doors here: a release, a change to the write gate or to write-path semantics, anything
  run against a real Calibre library. For these, run `code-review` from a fresh session, not the one
  that wrote the diff ([code-review docs]).
- In `pr` the author grades its own change. Distrust a "two-way, small" call, and give `pr` the issue,
  not only the diff ([pr docs]).
- Split a large diff into stacked PRs: two-way doors first, the one-way door last. Ship behind a flag
  if the new path must land dark. The one-way door gets a mandatory human review; the rest is reviewed
  for taste. Ask for the split explicitly: `/implement-spec` yields one branch, and upstream declined
  to build stacking into it ([v1.3 post]; [#1323], closed 2026-10-30).
- Treat each review comment as a hypothesis about the agent's environment. When the fix is mechanical,
  make it a rule (see `/retro` below) instead of fixing only this diff.
- A comment that explains a workaround is a smell. Fix the workaround, move the reason into an ADR, or
  name a test after it ([CODING_STANDARDS.md](../../CODING_STANDARDS.md): invariants in code, not
  comments).

## Where the skills write here

- **Glossary:** `GLOSSARY.md` at the root.
- **ADRs:** `docs/dev/adr/` with `D-NNN` numbers, gitignored and local-only. Layout and shape:
  [domain.md](domain.md).
- **Tickets and triage:** GitHub issues via `gh` ([issue-tracker.md](issue-tracker.md)), labels in
  [triage-labels.md](triage-labels.md). Tickets from `/to-tickets` are already agent-ready: skip `/triage`.
- **Specs:** a GitHub issue, never a file in the repo. `/to-spec` labels it `ready-for-agent`: remove
  the label after `/to-tickets`, so only tickets read as work orders. Close the spec when the work ships
  and never maintain it; what must outlast it goes into `GLOSSARY.md`, an ADR or `docs/TOOLS.md`
  ([to-spec docs], CC-065).
- **Handoffs:** `/handoff` writes to `$TMPDIR`, which a reboot empties. If the next session does not
  start within the hour, move the file into `docs/dev/` (gitignored). Give the next session the path,
  not pasted text, and first downgrade any claim the session did not verify ([handoff docs]).

## Gates the skills must pass

- **`tdd` seams** are the ones `CLAUDE.md` already enforces: tool handlers and domain code stay SDK-free,
  and `src/app/` use-cases reach adapters only through ports (`test/architecture.test.ts`). Test through
  those seams, and use `codebase-design` vocabulary when choosing a new one. `/implement-spec` has no
  step where seams are agreed with Artem, so name them in the spec or the tickets
  ([implement-spec docs]).
- **"Full test suite" in `/implement` and `/implement-spec`** means the hand-back gate in
  [`AGENTS.md`](../../AGENTS.md), including `pnpm build && pnpm catalog:check` when a tool or its schema
  changed.
- **`code-review` Standards axis** reads [`CODING_STANDARDS.md`](../../CODING_STANDARDS.md); the Spec axis
  reads the originating GitHub issue.
- **`pr` writes only the body.** The title must be a Conventional Commit (`conventional-title` check).
  Release-please reads commit types to pick the next version, so choosing `feat`, `fix` or `docs` is
  part of the door call. Rewrite the body after the PR changes; `pr` does not refresh it ([pr docs]).
- **`/retro` findings** land as a deterministic check (oxlint rule, test, CI job) when the mistake is
  mechanical, and in `CODING_STANDARDS.md` only when it is a judgement call. Retro proposes; Artem applies.
  Feed it the run's session transcripts and the PR review comments (`gh`). A new check that existing
  code already breaks is ratcheted: baseline today's violations, block new ones, tighten over time.
  A finding about a skill itself goes to `mattpocock/skills` as an issue, and only on Artem's go-ahead,
  because that repo is public.
- **`/retro` cadence:** after a session that went badly, or on a sample; never automatically, never in
  a loop ([v1.3 post]). After an overnight wave, add `docs/dev/overnight-<date>.md` to its inputs. Drop
  a candidate you cannot trace to a moment in the session, and prune old checks by hand: retro sees one
  session and never retires a rule ([retro docs]).
